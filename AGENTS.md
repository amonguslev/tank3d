# Правила роботи агентів у проєкті (Orchestrator + Subagents + STATE.md)

Ці правила діють постійно для всього робочого простору `C:\Users\among\Projects\tank`.

## 1. Архітектура ролей: Оркестратор та Рев'ювер (Carbon) + Суб-агенти (`flash` / `flash_lite`)

1. **Головний агент (модель Carbon) — Оркестратор і Рев'ювер**:
   - Не виконує об'ємну рутинну реалізацію самостійно, а координує роботу.
   - Аналізує запит користувача та актуальний стан у [STATE.md](./STATE.md).
   - Проєктує архітектурне рішення та розбиває задачу на чіткі атомарні підзадачі.
   - Делегує виконання підзадач суб-агентам через `invoke_subagent`.
   - Після отримання результату від суб-агентів **обов'язково проводить рев'ю**: перевіряє змінені файли, узгодженість типів, відсутність регресій, коректність збірки та відповідність вимогам користувача. За потреби надсилає правки суб-агенту через `send_message`.

2. **Суб-агенти — Виконавці зі швидшими та дешевшими моделями**:
   - Користувач явно встановив правило використовувати дешевші та швидші моделі для суб-агентів (замість `inherit`):
     - `Model: "flash"` — стандартний вибір для написання й редагування коду, створення нових модулів, верстки, ігрової/3D-логіки (`TypeName: "self"`) або дослідження кодової бази (`TypeName: "research"`).
     - `Model: "flash_lite"` — вибір для простих, дрібних, шаблонних або масових задач (точкові правки конфігурацій, текстів, документації, прості перевірки).
   - Незалежні задачі слід запускати паралельно кількома суб-агентами (слідкуючи, щоб вони не редагували один і той самий файл одночасно, або ізолюючи їх через `Workspace: "branch"` / `"share"`).
   - Кожному суб-агенту передавай чіткий контекст: які файли читати/змінювати, критерії готовності та що саме повернути у звіті.

## 2. Підтримка актуального стану проєкту в `STATE.md`

1. Файл [STATE.md](./STATE.md) у корені проєкту є **єдиним джерелом правди (Single Source of Truth)** про поточний стан гри та інфраструктури.
2. **Перед плануванням змін** оркестратор обов'язково переглядає `STATE.md`, щоб врахувати поточну архітектуру, структуру модулів та технічні особливості середовища.
3. **Після кожної зміни в проєкті** (додавання або зміна фіч, файлів, залежностей, налаштувань збірки/PWA, виправлення помилок чи зміна планів) файл `STATE.md` **має бути оновлений** у межах тієї ж задачі.
4. У `STATE.md` підтримуються актуальними:
   - поточний статус і стек проєкту;
   - карта файлів і модулів;
   - перелік реалізованих можливостей;
   - особливості локального середовища та запуску;
   - історія останніх змін (Changelog) і відкриті задачі / наступні кроки.

## 3. Обов'язкове використання Git (Контроль версій)

1. Уся розробка в `C:\Users\among\Projects\tank` ведеться з використанням **Git** (шлях до бінарника на цій машині: `"C:\Program Files\Git\cmd\git.exe"`, оскільки `git` не додано до системного `PATH`).
2. Службові та згенеровані директорії (`node_modules/`, `dist/`, `dev-dist/`, `.vite-temp/`) мають залишатися в [.gitignore](./.gitignore) і не потрапляти до індексу.
3. **Атомарні коміти після рев'ю**:
   - Після завершення кожної логічної фази або задачі — коли оркестратор провів код-рев'ю, перевірив типи/збірку та оновив `STATE.md` — зміни обов'язково фіксуються у Git осмисленим комітом (`git add` + `git commit`).
   - Під час паралельної роботи кількох суб-агентів у спільному робочому просторі (`Workspace: "inherit"`) суб-агенти не виконують `git commit` чи деструктивні git-команди (`git reset`, `git checkout --`), щоб не пошкодити файли сусідніх агентів; фіксацію комітів координує Оркестратор після завершення хвилі.
